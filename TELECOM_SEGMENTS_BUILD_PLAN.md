## Owner decisions (taken 2026-11-16, owner: "you decide"; follow the recommendations)
1. The default "Scratch Cards" category may be given a provider while it has no products (`CATEGORY_PROVIDER_LOCKED` once it has products). Legacy products (provider-less category) have segment `legacy` and cannot be sold/purchased after the migration.
2. A purchase with cards of several providers is refused `MIXED_SEGMENTS` (400, "split the bill by provider").
3. A Telecom stocktake belongs to ONE provider's Cards segment.
4. A correction of an entry-chosen record (expense, capital, cash drawing, transfer) keeps the original's segment by default; the caller may supply another segment. Reload/EZCash/top-up replacements derive the segment from the provider.
5. The opening balance is one per scope (book + segment [+ fund]).
6. Transfers between two Telecom segments are allowed (Telecom net 0 in the transfers report).
7. The dashboard "day not closed" reminder is per segment with activity.
8. Legacy closings can be reopened and re-closed; no new legacy closing; legacy records can be voided (their reversal stays `legacy`).

## Data model (frozen)
- `segment TEXT`; codes `dialog_cards, dialog_reloads, mobitel_cards, mobitel_reloads, airtel_cards, airtel_reloads, hutch_cards, hutch_reloads` plus `legacy` (rows from before the migration; never allowed on a new row except a reversal of a legacy original). NULL = not a Telecom row (Shop, Ice Cream). Exactly mirrors how `fund` works for Ice Cream: segment is named exactly when `book = 'telecom'`.
- Provider -> segment: `lower(reload_providers.name) || '_reloads'` / `'_cards'` (provider names are immutable, set of 4 fixed). EZCash and wallet top-up = `dialog_reloads`. Reload and provider top-up = provider + reloads. Card product/sale/purchase/loss/stocktake = the product's category provider + cards.
- Stored `segment` column: cash_entries, daily_closings (rebuilt), cash_counts, capital_entries, owner_drawings, expenses, purchases, stock_losses, stocktakes, reload_sales, ezcash_sales, telecom_topups, sales (rebuilt), cash_transfers `from_segment`/`to_segment` (rebuilt). `categories.provider_id REFERENCES reload_providers(id)` (ADD COLUMN, Telecom categories only, locked once the category has products).
- Derived: sale_items, purchase_items, stocktake_items, sales_returns, purchase_returns, return items (from the header); stock_movements/products via view `v_product_segment(product_id, book, segment)`.
- Per-table domain CHECKs: reload_sales/ezcash_sales/telecom_topups only `*_reloads` + legacy; sales/purchases/stock_losses/stocktakes only `*_cards` + legacy; others all 8 + legacy. BEFORE INSERT triggers: telecom needs segment, other books forbid it, `legacy` refused on INSERT (except a reversal row of a legacy original); `BEFORE UPDATE OF segment` aborts (immutable). Reversal mirror and transfer-link triggers also compare segments. A non-reversal cash entry's segment must equal its owning record's segment (026).
- Triggers around the view: provider on a category only for telecom and only while it has no products; a new Telecom stock product needs a provider-linked category (`PRODUCT_NEEDS_PROVIDER`, INSERT only); changing the category of a Telecom stock product with movements is refused if the segment would change (`PRODUCT_SEGMENT_LOCKED`).

## Test strategy
Invariants after every flow and in the randomized test: Telecom total = sum of the segments (balance, ledger totals, closing, P&L lines, valuation, transfers report); per-segment cash book = sum of its entries (opening + in - out = closing); a day closed for Dialog Reloads stays open for Mobitel Cards, ordering rule per segment; reversal/return/void entries stay in the original segment; corrections keep or take the supplied segment and a failed replacement leaves the original posted; restore validation fails for each corrupted segment invariant; Combined P&L, dashboard totals, Shop and Ice Cream figures equal the frozen fixture numbers. Independent-model randomized test (pure in-memory arithmetic model driven through the HTTP API, precedents `phase19-model-ledger.test.ts`, `phase11-fin-random.test.ts`). Existing tests that legitimately change are fixed at the helper level first (B): Telecom products now need a provider category; Telecom cash/closing/expense/capital/drawing/transfer calls need a segment; raw-SQL inserts of Telecom rows need segments; schema-shape tests (`phase20-closedday-migration`, `phase14-migrations`, `migrate`, `phase22-restore-validation`, `phase19-backup-restore`) and report-shape tests gain the new fields. Never weaken an assertion; extend expected values and explain each changed test in the report.
